Week 4: Replicating week 2's visitor counter

Welcome to my fourth linux project! This site is running on a clone server of the week 2 setup.

In this project, I have replicated the visitor counter from week 2. This site does not increment the counter, but simply mirrors the counter value from week 2's site

The visitor counter is stored in a MySQL database. Whenever the week 2 page is visited or refreshed, the Flask application updates the counter by executing SQL queries and displays the current total. Counter values are synchronized between the two sites, but only the server A's week 2 site increments the counter.

Create server B by copying server A.

To copy the week 2 server setup, I created a snapshot of the week 2 server and rebuilt it on a new server using CSC's own web interface.

Configure hourly website backups from A to B.

I made a bash script for hourly website backups from A to B. The cron job executes a script on server B, that uses rsync to copy the HTML files from the week 2 server(A) to the new server's(B) /srv/backup/www/$date directory.

Script also maintains a log file of the backup process and keeps only the last 2 backups, deleting older ones. The script is executed every hour using a cron job.

I also successfully recovered the website from a backup.

Configure continuous MariaDB replication from A to B.

For database I did use MySQL instead of MariaDB (Was familiar with it, and started these task before there was info on week2, it was maybe a mistake because the guides on the course are made for MariaDB, but lets go with it now and try to adapt).

To make synchronization happen i used MySQL's own tools mysqldump and mysql replication. I made a dedicated replication user and used it exclusively for database replication. Replication account was granted only the replication privileges for replication purposes and was restricted to connections from server A.

Application users were restricted to read-only access to the database.

Why continuous replication does not replace historical backups?

Continuous replication is not same thing as historical backups. If something happens to data on the database on server A, maybe a dataloss or corruption, the changes would be replicated to server B, resulting in the loss of data on both servers. Because of this, it is important to have regular backups to ensure that the data can be restored in case of accidental deletion or corruption.

Replication protects against hardware failures and natural disasters, but it does not protect against human error or application bugs.

A summary of both server's storage layout and backup locations

Server A's website files are located in /var/www/html/ and the database is located in /var/lib/mysql/.

Server B's backup copies of the website files are located in /srv/backup/www/$DATE and the database is located in /var/lib/mysql/. This project is not using database backups, but uses continuous log_bin replication.

LEMP application and the website served by it are located in applications own directory in my home directory: ./project/linux_course/viikko$NUMBER

An explanation of the Linux users, database users, ownership and permissions used

Linux users:

The website runs through the standard Nginx service account. Administrative tasks are performed using the Ubuntu user with sudo privileges.

Database users:

The database is accessed by the root user with sudo privileges.

There is an replicator account used for database replication, which has limited privileges only for replication purposes and can only access the database from the replication source.

LEMP application has a user named visitorWatchmen for accessing the database. On server A this user has read and write privileges. On server B this user has only read privileges.

Ownership and Permissions:

The website files are owned by the Nginx user and have appropriate permissions for web serving. The database files are owned by the MySQL user and have restricted permissions for security.

The backup directories on server B are owned by the root user and have restricted permissions to ensure that only authorized users can access the backups.

Backup files were protected with following permissions: 

            sudo chown -R root:root /srv/backup
            sudo chmod 700 /srv/backup
