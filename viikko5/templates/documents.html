Chat app

This application is a chat interface built using Flask. Nginx forwards requests to the Flask application, which retrieves responses from an Ollama language model. Chat messages are stored in a MySQL database, allowing the conversation history to be reloaded using the same browser session ID.

Description of the pipeline: what runs on pull requests, what runs on main, and how a deployment is verified?

On pull requests, GitHub Actions installs the dependencies and runs ruff linting and pytest and checks the shell scripts.

On Push the same checks run first. If they pass, GitHub Actions connects to the server using repository secrets, copies the application files by rsync, and runs the deployment script. The script installs dependencies, applies the database schema, updates and checks the nginx configuration, and then restarts the chat service

Deployment is verified by checking that the application is running and responding to requests and its version number matches the expected version.

Linux users, database users, file ownership and permissions you used, and where the secrets are stored:

The application runs as the user 'chatapp', which is a system user with no login shell. The application files are owned by 'chatapp' and have permissions set to "750" for directories and "640" for files. The database user is also 'chatapp@localhost', and it has access only to the 'chatapp' database. The app reads its DB connection settings from environment variables.

Secrets, such as database passwords, are stored in a .env file that is readable only by the 'chatapp' user.

Secrets used in the deployment process are managed through GitHub Actions secrets.

How /viikko5/ was added to Nginx without affecting other sites or pages?

/viikko5/ was added as a snippet to the Nginx configuration file by include snippets/chatapp.conf;. This is the path to the snippet that is created by the deployment script. The snippet contains the location block for /viikko5/ and the proxy settings for the Flask application. This way it does not interfere with other sites or pages served by Nginx.

Model choice and the server's memory and disk usage:

I ended up choosing the llama3.1:8b model for its performance and efficiency in handling the chat application. I tested many options and found this model to be the best balance between performance and resource usage. Other models were considered but did not offer the same level of performance under the given constraints.

If you completed Week 4: whether the chat database is replicated to server B, and why or why not?

In my replication setup there is no restrictions on the database replication in binlog_do_db or replicate_do_db. I have not set up any restrictions on the replication, so the chat database is replicated to server B. I might look into setting up restrictions in the future for more granular control.
